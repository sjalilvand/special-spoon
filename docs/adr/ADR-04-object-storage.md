# ADR-04 — Object Storage سازگار S3 (MinIO) برای فایل‌های سامانه

- **وضعیت:** پذیرفته‌شده — آداپتور پلاگین‌پذیر پیاده شد (0.37.0)؛ گام‌های ۱–۲ طرح مهاجرت عملیاتی شد (0.38.0)
- **زمینه مصوب:** بند Object Storage سند جامع — «جایگزینی دایرکتوری محلی فایل‌ها (B39)»
- **مرجع‌های مرتبط:** ADR-02 (صف کار)، B39 (فایل امن)، بند «فایل و امنیت» سند

## ۱) زمینه

فایل‌های سامانه (مدارک پرونده، رضایت‌نامه‌ها، ورودی‌های کارتابل) از فاز ۲۵ در
**دایرکتوری volume محلی** کنار نمونه API ذخیره می‌شوند: کلید ذخیره و
checksum در پایگاه داده، بایت‌ها روی دیسک، دانلود فقط با بلیت امضاشده
کوتاه‌مدت HMAC از مسیر سرور. این انتخاب برای «نسخه اول تک‌نمونه‌ای» درست بود،
اما با رشد سامانه چهار نقص ساختاری دارد:

| نقص | توضیح |
|---|---|
| تک‌گره بودن | volume به یک نمونه چسبیده است؛ چندنمونه‌ای شدن API (خواسته ADR-02) با دایرکتوری محلی ممکن نیست |
| بکاپ و بازیابی | بکاپ دستی فایل‌سیستم جدا از بکاپ پایگاه داده؛ بدون سیاست نگهداشت و lifecycle |
| سقف دیسک و انباشت | رشد بدون حد با حجم دیسک سرور گره خورده؛ جابه‌جایی به storage بزرگ = downtime |
| بدون replication | خرابی دیسک = از دست رفتن دائمی مدارک بالینی (ریسک حاکمیت داده B41) |

## ۲) تصمیم

لایه ذخیره‌سازی فایل به **آداپتور پلاگین‌پذیر Object Storage** منتقل می‌شود با
دو پروایدر:

- **`local`** (پیش‌فرض): همان دایرکتوری volume فعلی — بدون کلید، بدون وابستگی،
  قطعی؛ مناسب توسعه و استقرار تک‌نمونه‌ای؛
- **`s3`**: هر سرویس سازگار S3 — **MinIO self-hosted** گزینه پیشنهادی تولید
  (بدون خروج داده از سازمان — مهم برای داده بالینی) و AWS S3/Wasabi سازگار؛
  فعال‌سازی فقط با `S3_ENDPOINT_URL + S3_BUCKET + S3_ACCESS_KEY + S3_SECRET_KEY`.

الگوی دقیقاً همان D02/D03/D07/B28 است: تعویض پروایدر فقط با config، نبود کلید
یا خطای سرویس → **fallback به local (fail-soft)** با گزارش شفاف، و **کلیدها
هرگز به کلاینت/لاگ/پاسخ API نمی‌روند**.

*اصل محافظت‌نشده خروج از دامنه:* قرارداد امنیت B39 عوض نمی‌شود — دانلود همچنان
فقط با بلیت امضاشده کوتاه‌مدت از مسیر سرور انجام می‌شود و **presigned URL عمومی
S3 به کاربر داده نمی‌شود** تا «کنترل مجوز در هر بار دانلود» و audit حفظ شود.

## ۳) راه‌حل میانی فعلی (پیاده‌سازی 0.37.0)

1. سرویس `app/services/object_storage.py` — نمایه واحد
   `store / open_bytes / remove / storage_status` روی دو پروایدر؛
2. ستون **`files.storage`** (`local|s3`) — پروایدر واقعیِ ذخیره هر فایل ثبت
   می‌شود؛ دانلود/اسکن مجدد همیشه از پروایدرِ ردیف می‌خواند نه config جاری؛
   مهاجرت تدریجی (فایل قدیمی local، فایل جدید s3) بدون توقف سرویس ممکن است؛
3. خطای آداپتور S3 در آپلود → ذخیره محلی با همان کلید + ثبت
   «fallback» در scan_detail و audit — فایل هرگز گم نمی‌شود؛
4. شفافیت عملیاتی: بخش `storage` در `GET /integrations/config` (وضعیت
   بک‌اند فعال/پیکربندی‌شده، fallback، موجودی boto3، نام bucket — بدون هیچ کلیدی).

## ۴) شاخص‌های آستانه اجرا (چه وقت باید سوییچ کرد)

- چندنمونه‌ای شدن API آغاز شود (هم‌زمان با مسیر ADR-02)؛
- حجم انباشته فایل‌ها از **۵ گیگابایت** یا رشد ماهانه **۵۰۰ مگابایت** بگذرد؛
- SLA بکاپ/بازیابی مدارک رسمی شود (RPO تعریف‌شده)؛
- نیاز به lifecycle/expire خودکار (نسخه‌گذاری، قفسه‌بندی سرد) مطرح شود.

## ۵) طرح مهاجرت (۴ گام)

1. **زیرساخت (✅ عملیاتی شد در فاز ۳۸ — 0.38.0):** سرویس `minio` در
   `compose.yml` (پروفایل `storage` — بدون پورت عمومی مطابق بند ۱۳.۲؛
   تگ پین‌شده + healthcheck + volume اختصاصی `minio_data`) و `minio-init`
   (ساخت idempotent bucket + فعال‌سازی نسخه‌گذاری با `mc`)؛ در توسعه
   `compose.dev.yml` پورت ۹۰۰۰/۹۰۰۱ را باز می‌کند؛ `S3_ENDPOINT_URL`
   به‌طور خودکار در سرویس api تنظیم می‌شود؛ کلیدها از `.env`
   (`MINIO_ROOT_USER/PASSWORD`) می‌آیند؛
2. **مهاجرت داده (✅ عملیاتی شد در فاز ۳۸):** اسکریپت idempotent
   `backend/scripts/migrate_files_to_s3.py` (منطق: `app/services/storage_migration.py`)
   — پیمایش `files WHERE storage='local'` با سقف ردیف (`--limit`)،
   خواندن محلی، کنترل صحت checksum قبل از حرکت، `put_object` با همان
   `storage_key`، راستی‌آزمایی با خواندن مجدد از S3 و بروزرسانی
   `files.storage='s3'` فقط پس از تأیید؛ `--dry-run` بدون هیچ نوشتنی؛
   `--loop` تا اتمام؛ نسخه محلی حذف نمی‌شود (rollback = تنظیم ردیف به
   `local` بدون حرکت داده)؛ اجرای مجدد هر تعداد بار امن است؛
3. **سوییچ:** `STORAGE_BACKEND=s3` در config؛ fallback محلی به‌عنوان سپر
   خرابی فعال می‌ماند؛
4. **تسویه:** پس از پایداری، volume محلی فقط خواندنی و سپس حذف؛ local فقط
   برای توسعه/آزمون.

## ۶) پیامدها

**مثبت:** امکان چندنمونه‌ای شدن API؛ بکاپ/replication استاندارد S3؛ lifecycle
و نسخه‌گذاری؛ جدایی رشد داده از دیسک نمونه API؛ مسیر آماده برای فایل‌های
بزرگ‌تر (ویدیو آموزشی B33/B34) در آینده.

**منفی/هزینه:** یک مؤلفه عملیاتی جدید (MinIO) در دیپلوی و مانیتورینگ؛
مصرف شبکه در هر دانلود (بایت‌ها از سرور عبور می‌کنند — هزینه پذیرفته‌شده
کنترل مجوز)؛ وابستگی به boto3 در تصویر تولید.

## ۷) گزینه‌های ردشده

- **ادامه دایرکتوری محلی:** ریسک تک‌گره و بکاپ دستی — فقط برای توسعه؛
- **NFS/shared volume بین نمونه‌ها:** قفل‌های فایل و عملکرد نامطمئن؛
  lifecycle/replication ندارد و مدیریت بکاپ همان وضع دستی می‌ماند؛
- **presigned URL مستقیم به کلاینت:** کنترل مجوز و audit سرور دور زده
  می‌شود — خلاف بند B39 («کنترل مجوز در هر بار دانلود»)؛
- **DB BLOB (ذخیره بایت در PostgreSQL):** تورم WAL/بکاپ و فشار بر
  connection pool؛ برای مدارک چند‌مگابایتی نامناسب است.
