# ADR-05 — سقف نرخ سراسری (Rate limit) و Idempotency-Key عملیات مالی

- **وضعیت:** پذیرفته‌شده و اجراشده کامل — گام ۳ در 0.42.0، گام‌های ۱–۲ در 0.43.0 (مستند در نسخه 0.36.0 به‌عنوان بدهی)
- **زمینه مصوب:** بند ۱۰ سند جامع (Rate limit per-endpoint) + «Idempotency-Key
  برای عملیات مالی آتی»
- **مرجع‌های مرتبط:** ADR-02 (صف کار — نیاز به Redis مشترک)، B10 (سفارش/پرداخت)،
  B18 (کیف پول)، D07 (سقف نرخ دستیار)

## ۱) زمینه

سند جامع برای هر endpoint سقف نرخ می‌خواهد (بند ۱۰). پیاده‌سازی فعلی سقف‌های
per-feature سخت‌کد‌شده و in-process دارد:

| نقطه | سقف فعلی | مکانیزم |
|---|---|---|
| ورود (B02) | ۵ تلاش ناموفق در ۱۵ دقیقه برای هر کاربر | شمارنده در DB + قفل |
| OTP (B02-lite) | ۳ درخواست در ۱۰ دقیقه برای هر موبایل/هدف؛ ۳ تلاش اشتباه برای هر کد | شمارش ردیف‌های `otp_challenges` |
| نگهداشت اسلات (B09) | ۵ نگهداشت فعال برای هر IP | شمارش ردیف‌های `slot_claims` |
| دستیار هوشمند (B25) | ۳۰ پیام در دقیقه برای هر کاربر | پنجره لغزان in-process (`deque`) |
| دسترسی نقش‌دار | کنترل مجوز سمت سرور (`require_roles`) | خارج از بحث نرخ، برای شفافیت |

سه نقص ساختاری نسبت به خواسته سند: (۱) endpoint‌های «غیرحساس» سقف نرخ ندارند
و یک کلاینت معیوب می‌تواند بار بی‌مصرف بسازد؛ (۲) وضعیت سقف‌ها **in-process**
است — با restart گم می‌شود و بین چند نمونه (replica) مشترک نیست؛ (۳) سقف‌ها
پراکنده‌اند و سیاست واحد/قابل‌پیکربندی (مثلاً 429 با هدر `Retry-After`) وجود
ندارد. همچنین عملیات مالی (سفارش/پرداخت/تسویه/کیف پول) هم‌اکنون با قیود
یکتایی DB (callback تکراری بی‌اثر، `uq` روی استرداد/تسویه) محافظت می‌شوند،
ولی «قرارداد صریح Idempotency-Key» برای کلاینت‌های موبایل آتی (B17) و شبکه
ناپایدار تعریف نشده است.

## ۲) تصمیم

1. **سقف نرخ سراسری دو لایه‌ای:**
   - *لایه سرویس (سراسری، توزیع‌شده):* میان‌افزار Rate limit روی مسیرهای
     عمومی و حساس با پنجره لغزان مبتنی بر **Redis** (تک‌منبع حقیقت بین
     نمونه‌ها)؛ کلید: `(route, ip)` برای ناشناس و `(route, user_id)` برای
     احرازشده؛ پاسخ ۴۲۹ با هدر `Retry-After`؛
   - *لایه قاعده (per-feature):* سقف‌های منطقی فعلی (تلاش ورود، سقف OTP،
     سقف نگهداشت، سقف دستیار) عیناً باقی می‌مانند — سقف سراسری جایگزین
     قواعد دامنه‌ای نیست؛ روی آنها لایه محافظ اضافه است.
2. **Idempotency-Key برای عملیات مالی:** هر POST مالی (`/orders`,
   `/orders/{id}/payments`, تسویه‌ها، شارژ کیف پول) باید هدر
   `Idempotency-Key` (UUID کلاینت) بپذیرد؛ سرور کلید را با اثر عملیات
   (شناسه منبع ایجادشده + اثر انگشت payload) در جدول
   `idempotency_keys` ذخیره می‌کند؛ تکرار همان کلید → همان پاسخ قبلی
   (بدون ایجاد ردیف دوم). این قرارداد پیش‌نیاز اپ موبایل (B17) برای
   «دوبار-زَدن دکمه پرداخت» روی شبکه ناپایدار است.

## ۳) راه‌حل میانی فعلی (تا پیش از اجرا)

1. سقف‌های per-feature سخت‌گیرانه و آزمون‌شده (جدول بالا) + DB به‌عنوان
   منبع حقیقت شمارنده‌های حساس؛
2. تک‌نمونه‌ای بودن API به‌عنوان فرض عملیاتی (Nginx → یک نمونه api)؛
3. قیود یکتایی DB به‌عنوان خط دفاعی دوم عملیات مالی (callback بی‌اثر،
   `uq` سفارش-در-صورتحساب، منع استرداد مازاد)؛
4. سقف نرخ دستیار هوشمند (D07) در-process با سقف ۳۰/دقیقه/کاربر — پذیرفته
   که با restart ریست می‌شود (ریسک پایین، پنجره کوتاه).

## ۴) شاخص‌های آستانه اجرا

- استقرار بیش از **یک نمونه API** (مقیاس افقی) — سقف‌های in-process ناکارا
  می‌شوند؛
- بروز حملات سوءاستفاده واقعی (اسکن/فشار روی مسیرهای عمومی مثل
  `/public/*` و `/branch-map`)؛
- عرضه اپ موبایل (B17) با عملیات پرداخت — الزام Idempotency-Key واقعی؛
- یکسان‌سازی رفتار ۴۲۹ برای مشتریان اداری (سازمان‌ها B21) با SLA.

## ۵) طرح اجرا (۴ گام)

1. **زیرساخت مشترک:** Redis از طرح ADR-02 (Broker) برای شمارنده‌ها هم
   استفاده می‌شود — بدون مؤلفه جدید؛ کتابخانه: `slowapi` یا پیاده‌سازی
   کوتاه token-bucket با `redis-py`؛
2. **میان‌افزار لایه سرویس:** سقف پیش‌فرض (مثلاً ۱۲۰ درخواست/دقیقه/IP روی
   مسیرهای عمومی؛ ۶۰/دقیقه/کاربر روی مسیرهای احرازشده) + override
   per-route در Settings؛ ثبت ۴۲۹ در audit با نرخ نمونه‌برداری؛
3. **Idempotency-Key:** جدول `idempotency_keys (key PK, endpoint,
   payload_hash, response_snapshot, created_at)`؛ اعمال ابتدا روی
   `POST /orders` و `POST /orders/{id}/payments`؛ پاسخ تکرار از snapshot؛
   پاک‌سازی ردیف‌های باقی‌مانده بیش از ۲۴ ساعت توسط beat (ADR-02)؛
4. **آزمون و مستندسازی:** آزمون موازی‌سازی (دو درخواست هم‌زمان با کلید
   واحد → یک منبع) و آزمون ۴۲۹؛ مستندسازی هدرها در OpenAPI برای کلاینت‌ها.

## ۶) پیامدها

**مثبت:** سیاست واحد و قابل‌پیکربندی؛ محافظت یکسان بین نمونه‌ها؛ پاسخ ۴۲۹
استاندارد با `Retry-After`؛ امنیت عملیات مالی موبایل با Idempotency-Key؛
کاهش سطح حمله DoS نرم.

**منفی/هزینه:** وابستگی عملیاتی به Redis برای مسیر درخواست (اگر Redis
محو شود: خطای باز (fail-open) انتخاب می‌شود — ترجیح دسترس‌پذیری بر
سقف‌گیری دقیق، با ثبت هشدار)؛ یک جدول و نگهداشت جدید برای idempotency؛
ریسک سقف‌های تنگ برای مشتریان قانونی (حل با override per-route و
whitelist توکن‌های سرویس).

## ۷) گزینه‌های ردشده

- **سقف در Nginx (limit_req):** سریع است ولی آگاه از هویت/نقش نیست و برای
  ۴۲۹ هوشمند per-user قابل‌گسترش نیست؛ می‌تواند لایه صفر کمکی بماند؛
- **شمارنده در حافظه با هم‌رسانی گام‌به‌گام بین نمونه‌ها:** پیچیدگی همگام‌سازی
  بدون منبع حقیقت — بی‌معنا وقتی Redis در دسترس است؛
- **Idempotency فقط با قیود یکتایی DB:** برای «سفارش از نوبت» کافی است ولی
  برای «سفارش آزاد/شارژ کیف پول» کلید کلاینت‌محور لازم است (دو درخواست
  قانونی متفاوت نباید به دلیل قید یکتا ۴۰۹ بگیرند).

## ۸) وضعیت اجرا — به‌روزرسانی فاز ۴۲ (0.42.0): گام ۳ طرح کامل شد

**Idempotency-Key واقعی عملیات مالی** مطابق همین سند پیاده شد:

- **جدول `idempotency_keys`** (migration 0026) با ستون‌های طرح + قرارداد
  روشن: `response_snapshot` SQL NULL = رزرو «در جریان» (ستون با
  `none_as_null=True` تعریف شد تا None پایتون همیشه SQL NULL بنشیند)؛
- **میان‌افزار `app/core/idempotency.py`** — الگوی دو-فازی: رزرو اتمیک کلید
  (PK یکتا؛ مسابقه هم‌زمانی با IntegrityError حل می‌شود) → اجرای عادی
  هندلر → ثبت snapshot پاسخ موفق JSON؛ خطا/پاسخ غیر-JSON → آزادسازی رزرو؛
  جایگاه: داخل‌تر از پاکت v2 (بازپخش روی v2 هم پاکت‌بندی می‌شود) و
  بیرونی‌تر از محافظ NUL (رد 422 هم رزرو را آزاد می‌کند)؛
- **اعمال ابتدایی طبق طرح:** `POST /orders` و `POST /orders/{order_id}/payments`
  روی هر دو پیشوند v1/v2 — ثبت با مسیر نرمال‌شده (بدون پیشوند نسخه) تا یک
  کلید بین دو نسخه بازپخش شود؛ استفاده همان کلید روی منبع دیگر → ۴۰۹؛
- **سمنتیک‌های تکمیلی:** همان کلید + بدنه متفاوت → ۴۰۹ (بازپخش بی‌صدای
  پاسخ متفاوت ممنوع — الگوی Stripe)؛ کلید در جریان → ۴۰۹ با راهنمای تلاش
  مجدد؛ رزرو رهاشدهٔ کهنه (TTL ۶۰۰ ثانیه — سقوط سرور بین دو فاز) →
  جایگزینی اتمیک با شرط WHERE pending (کلاینت هرگز قفل دائمی نمی‌شود؛ ریسک
  اجرای مجدد در همین حالت خاص با قیود یکتایی DB مهار می‌شود — بند ۳ راه‌حل میانی)؛
- **پاک‌سازی ۲۴ ساعته (بند گام ۳ طرح):** روت ادمین `POST /api/v1/idempotency-keys/purge`
  (فقط SYSTEM_ADMIN + audit) + پاک‌سازی تنبل ساعتی داخل رزرو — تا
  عملیاتی‌شدن beat صف کار (ADR-02)؛ آمار در `GET /api/v1/idempotency-keys`؛
- **مستندسازی OpenAPI (بخش گام ۴):** هدر در دو روت مالی با توضیح قرارداد
  برای کلاینت‌ها؛ پاسخ بازپخش هدرهای `Idempotency-Key` و
  `Idempotency-Replayed: true` دارد؛ آزمون هم‌زمانی دو-نخ با کلید واحد →
  فقط یک منبع (بخش آزمون گام ۴)؛ آزمون ۴۲۹ به گام‌های ۱–۲ (سقف نرخ Redis)
  موکول است.

## ۹) وضعیت اجرا — به‌روزرسانی فاز ۴۳ (0.43.0): گام‌های ۱–۲ — طرح بسته شد

گام‌های ۱–۲ طرح (سقف نرخ سراسری دو لایه‌ای) مطابق سند پیاده شد:

- **زیرساخت مشترک (گام ۱):** سرویس `redis` در compose (redis:7.4-alpine،
  AOF، بدون پورت عمومی — بند ۱۳.۲)؛ کلاینت مشترک `app/core/redis_client.py`
  با اتصال تنبل، بازمصرف اتصال و تلاش دوبارهٔ ۳۰ ثانیه‌ای — همان Redis
  آیندهٔ Broker صف کار ADR-02؛ خالی بودن `RATE_LIMIT_REDIS_URL` = غیرفعال؛
- **میان‌افزار لایه سرویس (گام ۲):** `app/core/rate_limit.py` +
  `app/services/rate_limit.py` — پنجره لغزان ZSET با pipeline اتمی؛ کلید
  `(route, user_id)` برای احرازشده و `(route, ip)` برای ناشناس؛ route با
  فروریختن شناسه‌ها (عدد/UUID/هش → `:id`) نرمال می‌شود تا مسیرهای پارامتری
  سطل واحد داشته باشند و حدس شناسهٔ تازه سقف را دور نزند؛ سقف پیش‌فرض
  ۱۲۰/دقیقه ناشناس و ۶۰/دقیقه احرازشده + override per-route در Settings
  (کلید «METHOD مسیر» دقیق، «* مسیر» یا پیشوندی با «*» پایانی — با مسیر
  کامل یا بدون پیشوند نسخه) + whitelist `user_id`های بی‌سقف برای
  توکن‌های سرویس/مشتریان اداری SLA-دار؛
- **۴۲۹ استاندارد:** هدر `Retry-After` دقیق (بر پایه زمان خروج
  قدیمی‌ترین عضو از پنجره) + `X-RateLimit-Limit/Remaining` برای مشتریان
  SLA-دار (آستانهٔ بند ۴)؛ بدنه قرارداد v1 — روی v2 با کد `rate_limited`
  پاکت‌بندی می‌شود (میان‌افزار بین پاکت v2 و میان‌افزار مالی idempotency
  نشسته است: درخواستِ ردشده هرگز رزرو کلید idempotency نمی‌کند)؛
- **audit با نمونه‌برداری (بند گام ۲ طرح):** ثبت رخداد `rate_limit.429`
  با نرخ `RATE_LIMIT_AUDIT_SAMPLE_RATE` (پیش‌فرض ۰٫۲) تا در حمله، سیل
  رد شدن‌ها به سیل نوشتن DB تبدیل نشود؛ شکست ثبت بی‌اثر است؛
- **fail-open (بند ۶ سند):** نبود/محو Redis → عبور درخواست با هشدار و
  تلاش دوبارهٔ اتصال بدون ری‌استارت — دسترس‌پذیری مقدم بر سقف‌گیری دقیق؛
- **تکمیل بخش آزمون/مستندسازی (گام ۴):** آزمون ۴۲۹ با Redis فیک
  درون‌حافظه (۱۸ آزمون: پنجره لغزان با ساعت تزریق‌شدنی، Retry-After
  دقیق، کلید‌بندی user/ip/XFF، سطل واحد مسیر پارامتری، پاکت v2،
  override دقیق/پیشوندی، whitelist، fail-open، audit نمونه‌برداری‌شده،
  معافیت سلامت/اسناد، OpenAPI) + مستندسازی ۴۲۹/Retry-After در OpenAPI
  دو روت مالی.

لایه قاعده (سقف‌های per-feature جدول بخش ۱) عیناً برقرار ماند — سقف
سراسری لایه محافظ اضافه است، نه جایگزین.

**وضعیت نهایی طرح:** هر ۴ گام اجرا شد (گام ۳ در فاز ۴۲؛ گام‌های ۱–۲ و
بخش آزمون/مستندسازی گام ۴ در فاز ۴۳). این ADR بسته است؛ تنظیم عملیاتی
سقف‌ها و overrideها بر اساس پایش مصرف، «نگهداشت جاری» است نه بدهی معماری.
