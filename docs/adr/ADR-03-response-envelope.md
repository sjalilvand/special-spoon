# ADR-03 — پاکت پاسخ استاندارد `{data, meta, errors}` با نسخه /api/v2

- **وضعیت:** پذیرفته‌شده — /api/v2 با پاکت استاندارد پیاده شد (نسخه 0.38.0)؛ مهاجرت فرانت‌اند تکمیل شد (0.39.0)؛ مهاجرت موبایل به v2 تکمیل شد (0.40.0 — گام ۳)؛ **انقضای v1 اعلام شد (0.41.0 — گام ۴، مرحله «اعلام»؛ حذف در چرخه انتشار بعد)**
- **زمینه مصوب:** بند «قرارداد API» سند جامع — «پاکت پاسخ استاندارد
  `{data, meta, errors}` و Idempotency-Key»
- **مرجع‌های مرتبط:** ADR-05 (Idempotency-Key عملیات مالی)، B10 (سفارش)،
  B17 (اپ موبایل — مصرف‌کننده اصلی قرارداد پایدار)، بند ۱۳ (استقرار)

## ۱) زمینه

قرارداد فعلی API (v1) پاسخ‌ها را «مستقیم» برمی‌گرداند: فهرست‌ها به شکل
`{items, total, page, ...}`، اشیا به شکل فلت و خطاها به شکل
`{"detail": ...}` FastAPI. این قرارداد از فاز ۲۱ پایدار است و فرانت
(React) و اپ موبایل (B17) روی آن سوارند، اما سه نقص ساختاری دارد:

| نقص | توضیح |
|---|---|
| بدون شناسه درخواست | ردیابی خطای کاربر در لاگ‌های سرور کور است؛ `request_id` استانداردی در پاسخ نیست |
| شکل خطا ناهمگن | خطاها گاهی `detail` رشته، گاهی فهرست اعتبارسنجی و گاهی بدنه سفارشی‌اند؛ کلاینت نمی‌تواند «یک بار» مدیریت خطا بنویسد |
| جای متادیتا ندارد | هر کلید اضافه (صفحه‌بندی، اکو Idempotency-Key، نسخه) یا در بدنه اصلی لِحاق می‌شود یا هدر می‌ماند که کلاینت‌ها نادیده می‌گیرند |

تغییر مستقیم شکل پاسخ v1 «تغییر شکننده» است — همه مصرف‌کنندگان فعلی
می‌شکنند؛ به همین دلیل سند تصمیم گرفت انتشار با نسخه‌بندی انجام شود.

## ۲) تصمیم

1. **نسخه دوم API (`/api/v2`) عرضه می‌شود** که همان روت‌های v1 را با
   **پاکت استاندارد** سند ارائه می‌دهد:

   ```jsonc
   // موفقیت
   { "data": <payload>, "meta": { ... }, "errors": null }
   // خطا
   { "data": null, "meta": { ... }, "errors": [ { "code", "message", "details"? } ] }
   ```

2. **قرارداد `meta`:** `request_id` (uuid هر درخواست — برای ردیابی در لاگ)،
   `timestamp` (ISO-8601 UTC)، `version="v2"` و `duration_ms`؛ اگر کلاینت
   هدر `Idempotency-Key` بفرستد، همان کلید در `meta` اکو می‌شود (زمینه‌سازی
   قرارداد ADR-05؛ ذخیره اثر سرور = گام ۳ آن ADR).
3. **فهرست‌ها:** در پاسخ‌های **واقعاً صفحه‌بندی‌شده** `{items, total/page/...}`،
   `items` به `data` می‌رود و بقیه کلیدها (`total/page/page_size/...`) داخل
   `meta.pagination` قرار می‌گیرند — قرارداد فهرست‌محور v2.
   **تدقیق 0.39.0:** تفکیک فقط با حضور نشانگر صفحه‌بندی
   (`total/page/page_size/limit/offset`) انجام می‌شود؛ پاسخ‌های تکی/ساختاری
   که کلید `items` آن‌ها اقلام داخلی خود شیء است (اقلام صورتحساب، سؤالات
   فرم، ردیف‌های خطای import، سرویس‌های تخصص، اعلان‌ها `{items, unread}`)
   **دست‌نخورده** در `data` عبور می‌کنند تا معنای شیء حفظ شود — در 0.38
   تفکیک بدون نشانگر، چنین پاسخ‌هایی را مخرب می‌کرد (کشف‌شده در مهاجرت
   فرانت و آزمون قرارداد).
4. **خطاها:** از بدنه `{"detail": ...}` FastAPI نگاشت می‌شود — رشته →
   `{"code", "message"}`؛ فهرست اعتبارسنجی 422 → نگاشت `loc/msg/type`؛
   کدِ پایدار از وضعیت HTTP (`unauthorized/forbidden/not_found/conflict/
   validation_error/rate_limited/...`) — کدها هرگز تغییر نمی‌کنند.
5. **v1 دست‌نخورده می‌ماند** (سازگاری کامل فرانت و موبایل فعلی)؛
   انتقال تدریجی کلاینت‌ها به v2 بدون مهلت قطع v1.
6. **دانلود فایل (B39) بدون پاکت** عبور می‌کند — پاکت فقط برای
   `application/json` است؛ بایت‌های فایل و هدرهای بلیت دست نمی‌خورند.
7. v2 در OpenAPI طرح نمی‌شود (`include_in_schema=False`) تا اسکیما
   تمیز بماند؛ مستند قرارداد همین سند و تست‌های قرارداد است.

## ۳) راه‌حل میانی فعلی (پیاده‌سازی 0.38.0)

1. میان‌افزار پاکت (`app/core/envelope.py`) فقط روی پیشوند `/api/v2`:
   موفقیت/خطا را پاکت می‌کند، پاسخ غیر JSON را عبور می‌دهد و هدرهای
   معنادار (`Set-Cookie`, `Retry-After`, `WWW-Authenticate`) را حفظ می‌کند؛
2. همان روت‌های v1 دو بار سوار شده‌اند (v1: قرارداد فعلی، v2: پاکت) —
   بدون کپی‌برداری روت‌ها؛ نگهداری یک‌مکان است؛
3. استثنای مدیریت‌نشده 500 (بدنه متنی) فعلاً بدون پاکت عبور می‌کند —
   لاگ استاندارد سرور حفظ می‌شود و نگاشت کامل خطاها تدریجی تکمیل می‌شود؛
4. آزمون قرارداد: `tests/test_phase38_envelope.py` (۱۱ آزمون — شکل پاکت،
   بالا آمدن `items`، خطاهای 401/404/422، اکو Idempotency-Key،
   دست‌نخوردگی v1 و خروج v2 از OpenAPI).
5. **(0.39.0) مهاجرت فرانت‌اند (گام ۲ طرح):** کلاینت HTTP فرانت روی
   `/api/v2` رفت — interceptor گشونده پاکت در `src/api/client.ts` تنها
   نقطه سازگاری است: `res.data` → payload واقعی، `res.meta` → متادیتا
   (augmentation تایپ axios)، پاسخ‌های blob (B39) بدون تغییر؛ توابع
   فهرست لایه api، شکل `{items, total, ...}` را از `meta.pagination`
   بازچینی می‌کنند تا صفحات تغییر نکنند؛ `errDetail` خطا را از
   `errors[0].message` می‌خواند (fallback `detail` حفظ شد)؛ جریان
   refresh: کوکی نشست از `path=/api/v1/auth` به `path=/api` رفت تا در v2
   نیز ارسال شود (باگ واقعی کشف‌شده در مهاجرت)؛ اعتبار با E2E واقعی
   (ورود از UI + بارگذاری اعلان‌ها) و ۳۰۲ آزمون pytest.
6. **(0.39.0) ردیابی کوکی v2:** کوکی refresh نسخه-agnostic است؛
   درگاه‌های refresh/logout هر دو نسخه از یک کوکی مشترک استفاده می‌کنند.
7. **(0.40.0) مهاجرت موبایل (گام ۳ طرح):** اپ B17 (`mobile/`) مستقیماً روی
   `/api/v2` رفت — نقطه واحد سازگاری `lib/api/api_client.dart`:
   پاسخ‌خوانی `data/errors`، پیام خطا از `errors[0].message` (fallback
   `detail` حفظ شد)، نگهداری `request_id` در `lastMeta` برای ردیابی
   پشتیبانی فنی B23؛ صفحات تغییری نکردند (همه پاسخ‌های مصرفی اپ
   `{items, unread}` و اشیای فلت‌اند که در v2 دست‌نخورده در `data`
   عبور می‌کنند — تدقیق 0.39.0).
8. **(0.41.0) انقضای اعلام‌شده v1 (گام ۴ طرح — مرحله «اعلام»):**
   میان‌افزار `app/core/deprecation.py` روی همه پاسخ‌های `/api/v1`
   (موفق و خطا) هدرهای استاندارد انقضا را ست می‌کند:
   `Deprecation: version="v1"` (پیش‌نویس IETF)، `Sunset: <HTTP-date>`
   (RFC 8594 — تاریخ از `V1_SUNSET_DATE`، پیش‌فرض 2027-04-20) و
   `Warning: 299`؛ v2 و بقیه مسیرها پاک می‌مانند. دو حالت عملیاتی:
   `V1_DEPRECATION_MODE=warn` (پیش‌فرض — فقط هدر، سازگاری کامل) و
   `readonly` (کلید اضطراری چرخه حذف — متدهای نوشتاری v1 با 410 Gone و
   بدنه قرارداد v1 رد می‌شوند و خواندن برقرار می‌ماند). به‌کارگیری
   `readonly` فقط پس از یک چرخه انتشار کامل با `warn` و پایش
   مصرف‌کننده جامانده؛ حذف کامل v1 = چرخه بعد از آن (فاصله الزامی سند).
   آزمون‌ها: `tests/test_phase41_adr_step4.py` (بخش اول).

## ۴) شاخص‌های آستانه مهاجرت کلاینت‌ها به v2

- آغاز توسعه اپ موبایل نسخه پرداخت‌دار (B17 با Idempotency-Key واقعی)؛
- افزودن هر مصرف‌کننده بیرونی جدید (همه روی v2 — v1 فقط برای
  مصرف‌کنندگان فعلی)؛
- نیاز به ردیابی خطای کاربر (پشتیبانی فنی B23) با `request_id`.

## ۵) طرح مهاجرت (۴ گام)

1. **عرضه v2 (انجام شد — 0.38.0):** میان‌افزار پاکت + سوار‌کردن دوباره
   روت‌ها + آزمون قرارداد؛ v1 بدون تغییر؛
2. **مهاجرت فرانت (انجام شد — 0.39.0):** کلاینت HTTP فرانت به v2 رفت
   (پاسخ‌خوانی `data/errors`) با رگرسیون کامل — tsc+build سبز، E2E واقعی
   سبز (ورود از UI/اعلان‌ها)، ۱۹ آزمون pytest جدید فاز ۳۹؛
3. **مهاجرت موبایل (انجام شد — 0.40.0):** اپ B17 مستقیماً روی v2
   (بدون گذر از v1) — کلاینت یک‌مکان `api_client.dart` پاکت را باز
   می‌کند؛
4. **انقضای v1 (اعلام شد — 0.41.0):** همه مصرف‌کنندگان شناخته‌شده روی v2
   هستند (فرانت فاز ۳۹، موبایل فاز ۴۰) — v1 با هدرهای
   `Deprecation`/`Sunset`/`Warning` منقضی اعلام شد (حالت `warn`)؛
   **مرحله بعد (چرخه انتشار بعدی):** حالت `readonly` (رد نوشتن‌ها با 410)
   و سپس حذف کامل v1 — با فاصله حداقل یک چرخه انتشار بین هر مرحله.

## ۶) پیامدها

**مثبت:** قرارداد واحد و پیش‌بینی‌پذیر برای همه کلاینت‌ها؛ ردیابی خطا با
`request_id`؛ مدیریت خطای «یک‌بار‌نوشت» در کلاینت‌ها؛ جای استاندارد برای
متادیتا (صفحه‌بندی، اکو Idempotency-Key)؛ پیش‌نیاز عملی Idempotency-Key
مالی ADR-05.

**منفی/هزینه:** دو قرارداد موازی تا اتمام مهاجرت (هزینه نگهداری تست‌ها
کمی بالا می‌رود)؛ خطر سردرگمی توسعه‌دهندگان جدید (حل با مستندسازی و
مثال در همین سند)؛ میان‌افزار پاکت‌بندی یک لایه پردازش بدنه اضافه دارد
(فقط روی v2 — اندازه‌گیری‌شده در `duration_ms`).

## ۷) گزینه‌های ردشده

- **تغییر درجا در v1:** همه مصرف‌کنندگان فعلی می‌شکنند — خلاف تصمیم سند؛
- **پاکت فقط برای خطاها در v1:** نیمه‌قرارداد بدتر از هر دو — کلاینت‌ها
  دو شکل موفقیت و سه شکل خطا می‌بینند؛
- **پاکت با هدر (X-Request-Id و ...):** هدرها در میان‌افزارهای شبکه حذف
  می‌شوند و در لاگ کلاینت دیده نمی‌شوند؛ قابل‌کشف نیستند برای توسعه‌دهنده
  موبایل؛
- **نسخه با هدر Accept (content negotiation):** پیچیدگی کش و پروکسی و
  نامرئی بودن در URL؛ نسخه‌بندی مسیرمحور شفاف‌تر است.
