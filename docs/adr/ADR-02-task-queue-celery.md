# ADR-02 — صف کار توزیع‌شده (Celery/arq) برای پردازش پس‌زمینه

- **وضعیت:** پذیرفته‌شده به‌عنوان بدهی فنی (مستند در نسخه 0.36.0)
- **زمینه مصوب:** بند صف کار سند جامع — «اعلان بیرونی، تولید PDF و اسکن فایل»
- **مرجع‌های مرتبط:** ADR-04 (Object Storage)، ADR-05 (سقف نرخ)، D02 (درگاه)، D04 (SMTP)

## ۱) زمینه

سامانه Rosepsy چند کار پس‌زمینه‌ای دارد که هم‌اکنون یا در مسیر درخواست اجرا
می‌شوند یا با صف‌های سطح پایگاه‌داده مدیریت می‌شوند:

| کار | پیاده‌سازی فعلی | ریسک وضع موجود |
|---|---|---|
| ارسال ایمیل اعلان‌ها (B12+/D04) | جدول `email_outbox` + `process_outbox` هم‌زمان و محدود | ارسال هم‌زمان در فراخوانی HTTP؛ مقیاس‌پذیری محدود به یک نمونه |
| ارسال پیامک اعلان‌ها (B28 فاز ۳۶) | جدول `sms_outbox` + آداپتور پلاگین‌پذیر log/kavenegar/smsir | همان بالا + تأخیر شبکه سرویس پیامک در مسیر `process` |
| ارسال مستقیم OTP (B02 فاز ۳۶) | فراخوانی REST سرویس پیامک در مسیر درخواست (فقط آداپتور کلیددار) | تأخیر/خطای سرویس بیرونی داخل زمان پاسخ درخواست کاربر |
| اسکن آنتی‌ویروس (B39-plus/ClamAV) | هم‌زمان در مسیر آپلود با سقف زمانی | فایل بزرگ/سرور شلوغ → آپلود کند؛ تلاش مجدد دستی |
| تولید PDF (فاکتور/گواهی — آتی) | هنوز پیاده نشده؛ تولید سمت سرور سنگین است | اجرای هم‌زمان می‌تواند نمونه API را اشباع کند |

این وضعیت برای «نسخه اول تک‌نمونه‌ای» عمداً انتخاب شد: پیچیدگی عملیاتی یک
Broker (Redis/RabbitMQ) و Worker در راه‌اندازی اولیه توجیه نداشت و قواعد
fail-soft (شکست ارسال هرگز جریان پرداخت/نهایی‌سازی را متوقف نمی‌کند) با
`SAVEPOINT` و صف DB برقرار شد. اما با رشد ترافیک و افزوده‌شدن کارهای سنگین،
سه نقص ساختاری پدیدار می‌شود: (۱) نبود تلاش مجدد زمان‌بندی‌شده با backoff،
(۲) نبود اجرای زمان‌بندی‌شده دوره‌ای (مثل `process_outbox` هر N ثانیه بدون
فراخوانی مدیر)، (۳) قفل‌شدن مقیاس به یک نمونه (صف in-DB بین چند Worker قابل
تقسیم است ولی زمان‌بندی و نرخ‌گذاری مرکزی ندارد).

## ۲) تصمیم

پردازش پس‌زمینه سامانه به **صف کار توزیع‌شده Celery با Broker Redis** منتقل
می‌شود (gRPC-free، پایتون‌محور، سازگار با SQLAlchemy sync sessions فعلی).
`arq` (بر پایه asyncio) گزینه دوم پذیرفته‌شده است؛ اگر در فاز مهاجرت، سرویس‌های
مرتبط async شده باشند، arq کوتاه‌تر مسیر است. تصمیم پیش‌فرض اجرا: Celery.

*اصل محافظت‌نشده خروج از دامنه:* این تصمیم «پیک کارر پس‌زمینه» را تغییر
نمی‌دهد — تزریق وابستگی‌ها، fail-soft و «شکست اعلان جریان اصلی را متوقف
نمی‌کند» باید پس از مهاجرت هم عیناً برقرار بماند.

## ۳) راه‌حل میانی فعلی (تا پیش از مهاجرت)

1. صف‌های DB (`email_outbox`, `sms_outbox`) با وضعیت صریح
   `pending/sent/failed/disabled` — بدون سیاه‌چاله؛
2. اجرای محدود و ایمن `process_*` با سقف ردیف و سقف تلاش (۵)؛
3. fail-soft کامل: خطای SMTP/REST پیامک هرگز سفارش/نهایی‌سازی/OTP را
   ناموفق نمی‌کند و در `last_error` ثبت می‌شود؛
4. شفافیت عملیاتی: `GET /email-outbox`، `GET /sms-outbox`،
   `GET /integrations/config` (بدون کلید) + ثبت اقدام در audit.

## ۴) شاخص‌های آستانه اجرا (چه وقت باید مهاجرت کرد)

- حجم ایمیل/پیامک از **۵۰۰ ردیف در روز** یا صف pending پایدار از **۲۰۰ ردیف**
  فراتر رود؛
- امکان‌سنجی چندنمونه‌ای شدن API (replica > 1) آغاز شود؛
- تولید PDF دوره‌ای/گروهی (گواهی‌ها، فاکتورهای سازمانی B21-plus) به backlog
  اضافه شود؛
- نیاز به بازآرایی زمان‌بندی‌شده (مثلاً یادآوری نوبت T-24h) مطرح شود.

## ۵) طرح مهاجرت (۴ گام)

1. **زیرساخت:** سرویس‌های `redis` و `worker` در `compose.yml`؛ تنظیمات
   `CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND` در Settings (بدون کلید در
   پاسخ‌های API)؛ نمونه‌های worker و beat جدا از api؛
2. **قرارداد وظایف:** هر وظیفه idempotent (کلید طبیعی: `email_outbox.id` /
   `sms_outbox.id` / `(entity, action)`)؛ payload فقط شناسه — «متن بالینی و
   کد OTP هرگز در پیام وظیفه/لاگ Broker نمی‌رود»؛
3. **انتقال تدریجی:** اول `process_outbox`/`process_sms_outbox` به beat
   (هر ۶۰ ثانیه) + وظیفه `retry_failed`؛ سپس اسکن ClamAV؛ سپس تولید PDF؛
   صف‌های DB به‌عنوان منبع حقیقت می‌مانند و Worker فقط مصرف‌کننده است
   (بدون تغییر طرح پایگاه‌داده)؛
4. **حذف مسیرهای هم‌زمان:** پس از پایداری، فراخوانی‌های مستقیم (OTP SMS در
   مسیر درخواست) به صف منتقل و endpoint‌های `*/process` مدیریت‌شده فقط
   برای اجرای فوری مدیر باقی می‌مانند.

## ۶) پیامدها

**مثبت:** تلاش مجدد خودکار با backoff؛ زمان‌بندی دوره‌ای بدون دخالت مدیر؛
مقیاس افقی Worker مستقل از API؛ رهگیری وضعیت هر وظیفه؛ امکان أولویت‌بندی
صف (اعلان < گزارش < PDF حجیم).

**منفی/هزینه:** دو مؤلفه عملیاتی جدید (Redis + Worker) در دیپلوی و مانیتورینگ؛
خطر دوباره‌اجرایی وظایف (با idempotency و صف DB به‌عنوان منبع حقیقت مهار
می‌شود)؛ پیچیدگی دیباگ (ردیابی بین API و Worker با `entity_id` در audit).

## ۷) گزینه‌های ردشده

- **ادامه صف DB بدون Worker:** سقف مقیاس و نبود backoff مرکزی — فقط برای
  نسخه تک‌نمونه‌ای پایدار است؛
- **cron خارجی (systemd timer) روی process endpoints:** احراز هویت
  endpoint مدیریتی، نبود retry هدفمند و رقابت چند نمونه؛
- **Kafka/RabbitMQ در فاز اول:** هزینه عملیاتی بالاتر از نیاز فعلی؛ Redis
  برای صف‌های سبک این سامانه کافی است.
